# Pull Request のレビュー

変更内容・CI・コード品質の観点で GitHub の Pull Request をレビューする。

## Usage

```
/pr-review            # 現在のブランチの PR をレビュー
/pr-review <PR_NUMBER> # 指定した PR 番号をレビュー
```

## Task

GitHub の Pull Request をレビューする。次の手順に従うこと。

1. **PR 情報の取得**
   - PR 番号が無ければ `gh pr view`（番号なし）で現在のブランチの PR を取得する
   - PR 番号が指定されていれば `gh pr view <PR_NUMBER>` を使う
   - `gh pr diff` で変更全体の diff を取得する

2. **変更内容の分析**
   - 変更されたファイルを以下の観点でレビューする:
     - コード品質・ベストプラクティス
     - 型ヒント（公開関数の引数・戻り値に型を付ける）
     - バグや不具合の可能性
     - パフォーマンス上の懸念
     - セキュリティ上の脆弱性
   - プロジェクトルール（`CLAUDE.md`）への準拠:
     - lint をミュート / 無効化していないか（`# noqa` の濫用、ruff ルールの無効化）
     - 環境変数のハードコードがないか
     - 秘匿情報（トークン・認証情報）をコミットしていないか

3. **よくある問題の確認**
   - lint / format エラー（`make check` が通るか）
   - 新規機能に対するテストの欠如
   - 命名の一貫性
   - 設定可能にすべきハードコード値
   - エラーハンドリングの欠如
   - 未使用の import や変数

4. **ビルドとテストの確認**
   - `gh pr checks` で GitHub Actions の状態を確認する
   - 全チェックが green ✓ であることを確認する
   - 失敗しているチェックがあれば:
     - どのチェックが失敗しているか特定する
     - `gh run view <RUN_ID>` で失敗ログを分析する
     - レビュー上のブロッカーとして記載する

5. **実ファイルの内容を読む**
   - diff だけに頼らず、Read で実際のコードを確認する
   - import・型定義・関連コードを確認し、変更が文脈上妥当か検証する

6. **構造化されたフィードバック**
   以下の形式で提示する:

   ### 概要
   [この PR が何をするかの簡潔な説明]

   ### GitHub Actions の状態
   [全チェックとその状態。承認には全て green が必要]

   ### レビューした変更
   [ファイルと主要な変更点を file:line 形式で]

   ### 検出した問題
   重大度別（Critical / Major / Minor）に整理する

   #### Critical
   [バグ・セキュリティ・データ破壊につながる問題。修正必須]

   #### Major
   [設計上の問題・パフォーマンス懸念。修正すべき]

   #### Minor
   [スタイル・規約・改善提案。直すと良い]

   ### 良い点
   [良い実装・うまい解決・読みやすいコードを挙げる]

   ### 提案
   [改善提案・ベストプラクティス]

   ### 承認ステータス
   - ✅ APPROVED - 全 green、Critical なし、マージ可能
   - ⚠️ APPROVED WITH COMMENTS - 全 green、Minor のみ、マージ可能
   - ❌ CHANGES REQUESTED - Critical あり or チェック失敗、マージ前に要修正

## Notes

- 承認前に必ず GitHub Actions が全て green であることを確認する
- diff だけでなく実ファイルを読み、全体の文脈を理解する
- 厳密かつ建設的に。問題点と良い点の両方を挙げる
- コード位置は file:line 形式で参照する
- GitHub Actions が失敗していたら自動的に CHANGES REQUESTED
